# Conversion tracking via Netlify Blobs and pushed result charts

---
status: accepted
---

Storyblok Experiments has **no event-ingestion endpoint**. The only write path for experiment outcomes is the Management API's `POST /v1/spaces/:space_id/experiments/:experiment_id/results`, which accepts a **pre-computed chart snapshot** (`{ charts: [{ kind, labels, series }] }`, max 20) and replaces the stored snapshot wholesale. Storyblok stores and displays the charts; it does no counting, no rate calculation, and exposes no per-visitor or per-event API. It is a "bring your own analytics, push the chart" model. That endpoint also requires a privileged OAuth/personal-access token, which must never reach the browser.

Those two facts rule out the obvious shape ("button click sends a conversion event to Storyblok"): there is nowhere to send a single event, and the only write needs a secret. So we **accumulate the tallies ourselves and push a computed chart**. The conversion button POSTs to a server-side Astro API route (`src/pages/api/conversion.ts`) that holds the Management token; that route updates a per-variant tally and pushes the recomputed charts via `storyblok-js-client` (a second client instance configured with `oauthToken` + `region` — never a hand-rolled request). Delivery reads continue through the existing delivery client.

The tally lives in **Netlify Blobs**, not in Storyblok. We considered making the pushed chart itself the source of truth (read-modify-write the results snapshot on every click) — zero extra infrastructure, but it overloads a presentation payload as a datastore and makes every read a Management API round-trip. We also considered an external analytics platform (overkill for a demo) and an in-memory counter (resets on cold start). Blobs gives a durable, low-latency key-value store so the **impression** path can record cheaply on the SSR hot path without an mapi call (honouring ADR-0001's fast, flash-free rendering), while the rarer **conversion** path does the Blobs read-modify-write *and* the chart push. The Blob also stores the variant roster (seeded from `experiment.variants`, which the delivery path already holds), so the endpoint needs no Storyblok read at push time.

Metrics are counted **per unique visitor** (impression once at first assignment via the existing `persist` stickiness hook; conversion once per visitor via an `sb_conv_<experimentId>` cookie) so the conversion rate is always ≤ 100% and credible on a call. Two charts are pushed: conversion rate by variant, and impressions/conversions by variant (sample size).

The trade-offs we accept: the feature is **Netlify-specific** (Blobs); read-modify-write is **racy** under concurrency (fine at demo traffic, the only writers being a presenter and sparse visitors); we keep only **current tallies, not timestamped events**, so no time-series/line charts and no recomputation of history; and a conversion arriving with **no roster in the Blob** (a visitor assigned before the feature existed, an evicted Blob, or a failed impression write) is **failed open** — the push is skipped rather than scrambling to refetch — consistent with the fail-open posture in the delivery path.
